# Using the UI

Paste a PR link (`.../pull/N`, `.../pull/N/files` or `owner/repo#N`) or a local Git checkout path into the UI to triage it. Local triage compares the checkout with the merge base of `origin/HEAD` (or `origin/main` / `origin/master`) and shows how many commits it is ahead and behind. It includes committed, staged, unstaged and untracked changes in the same hunk review. It uses a temporary Git index, so the checkout's index is untouched. A local result supports review notes, code context, walkthrough, code map and fixes. Fixes use a separate worktree at the checkout's current commit, so committing what was triaged doesn't need another triage. If the code, branch or merge base changed since triage, the fix still runs on the current code, with a warning in the fix banner and on the fixed result that the review is of the triaged code. If the checkout has uncommitted changes when a fix starts, the UI asks whether to commit them (with a message the summarizer writes) and fix in a worktree, or apply the fix in the current branch next to them. **Don't ask again** saves the answer, and Settings → Fix issues changes it.

The local result has a **Create PR** button. Commit any working tree changes and triage again before clicking it. The button pushes the current branch to `origin` and runs `gh pr create`, with the title taken from the commits. It writes the description from the overview: when the repository has a PR template (`pull_request_template.md` in `.github`, the root or `docs`, or a `PULL_REQUEST_TEMPLATE` directory holding one), the summarizer fills it in, keeping its headings. Otherwise the description is the overview's Why and How. The sequence diagram goes in as a Mermaid block, in the template's diagram section if it has one, or in a Sequence section at the end. The button waits up to two minutes for a diagram that is still being written, then opens the PR without one. If the commits are on the default branch, it creates and switches to a `pr-manager/<commit>` branch first. Pending review notes are copied to the new PR. The button checks that the branch and diff still match the triaged result.

When the branch already has an open PR, opened from PR Manager or anywhere else, the button is an orange **Update PR** next to an **Open PR** link. After a confirmation it pushes the branch and replaces the PR's description with one written the same way; the title is left alone. **Restore previous description** then puts back the description the PR had before the update.

The sidebar groups results by repository and lists each repository's changes (PRs, branches, commits and working trees) most recently used first: the later of the latest triage and the last time a person changed something on it, such as marking units reviewed, dismissing an issue, drafting a comment or fixing. Opening a result or moving between steps doesn't count. A repository lists 3 changes, then **Show N more**; Settings → *Review* → *Sidebar* sets how many (0 for all). The open result is always listed. A change not touched in 10 days (triaged, opened, or changed as above) is hidden; the same setting sets the days (0 keeps every change). Its results stay in the cache, so opening its link lists it again, and a line under the list counts the hidden changes and shows them. The ✕ on a row (shown on hover) deletes the change: all its results leave the cache, and triaging it again lists it again. It doesn't ask first unless *ask before a row's ✕ deletes a change* is checked in the same settings.

Every unit shows its bucket, impact, likelihood, review attention, reason, confidence, summary, score and any escalations, above its hunks. The unit's details show how the score picked its bucket. **details** lists the issues the review found (with a **→ draft comment** button when the line can take a GitHub comment) the code-map entry (matched symbol/file, CodeRank, rollback tags, dependent repos and top callers) and the likelihood factors with the measurements behind them. The PR header shows the highest impact, likelihood and attention. A small ↗ icon after the PR number, the repository, each branch and each commit opens it on GitHub or GitLab (a local checkout without a remote has none, and a local branch or commit not pushed yet has no page there).

A PR's badge, in the sidebar and the PR header, is colored by its state as on GitHub: green open, purple merged, red closed. The app keeps the state current without hammering GitHub (`prwatch.go`), and only for the PRs on screen: the sidebar's rows that aren't under **Show N more**, in a folded repository, hidden as untouched or in a hidden sidebar, and the result open. A PR is asked about with `gh` when it comes into view, so the ones listed when the app starts are asked about then, and a hidden one when **Show N more** (or unfolding its repository) shows it, unless it was asked about in the last minute. A PR still open is asked about again after 2 minutes, then twice as long each time, up to an hour, while it stays on screen. Opening a result asks again about the open PRs on screen in its repository (at most once a minute per repository), starting their backoff over, and about the PR opened, so a reopened PR is caught too. A PR found merged or closed is not asked about again. Every call waits 2 seconds after the one before it, so many PRs on screen are spread out rather than asked about at once. A changed state is saved on every result of the PR, and the sidebar reloads within 30 seconds.

## Review tab

The **Review** tab has three modes, switched at the right of the tab bar and remembered: **Walkthrough**, the default, **Files**, and **Classic**, every file and unit in one list. **Files** shows the PR's directory tree beside one file at a time. Each changed file is colored by its most important change (human review red, skim orange, auxiliary yellow-green, no review green), with its open issue count, and a collapsed directory shows the color of the most important file in it. The file opens first in human review, as the whole file at the PR head, with each change's review pinned beside its code, as in a grouped walkthrough step. **← / →** in the file bar move through the tree, and **Reviewed** marks every change in the file, sharing its progress with the walkthrough. Opening a change from the Issues, Sequence or Code map tab while in Files opens its file at that change. The walkthrough shows one step at a time, most important first: human review before skim, then by review attention, then by risk (impact × likelihood). By default a step groups related units (see *Grouping* below). Under the diff, the changed definitions the step's code uses from other files are listed collapsed, with a link to the step that reviews them, and open to show their diff. Settings → *Walkthrough steps* → *Grouping* sets what a step holds: **none** is one unit a step, **by file** is one file's changes in file order, and a file over 400 changed lines is split between units, which in practice splits large test files. **By relation**, the default, uses the links of `triage/group.go`: units that name each other (caller and callee), a test named after the symbol it exercises, and two small changes in one file, merged from the strongest link down up to 8 units and 400 changed lines a step. The step header says which links joined it. A grouped step is ranked and bucketed by its most important unit, starting with that unit's file. With grouping on, every step, including one with a single unit, has a row per unit: its review on the left, beside its code on the right, and pinned while that code scrolls past. Clicking a file's bar collapses the file to that bar, marked ✓ once its changes are reviewed, in every step it appears in, until it is clicked again; this is saved with the result's progress. A review starts collapsed to one line (bucket, symbol, headline, issue count) unless it is the step's only unit, the unit is in human review, or it has issues. This only changes how the PR is read, applies at once to every result, and is separate from the review grouping in `triage/group.go`, which only saves model calls. The design comes from `experiments/grouping-readability`. Auxiliary (tests, docs, fixtures) and "no review" units are left out unless you tick the box. Each step has the headline, and for each unit the issues ordered by severity (**show line** scrolls to the flagged line, which is marked in the diff), the review notes, the "what to check" list and why the unit is in its bucket, next to its diff. Comments and context expansion work the same as in Classic, and **↕ expand all** shows the whole file with other units' changes dimmed. The step bar is fixed to the bottom of the window: **← Previous** / **Next →** (or `←`/`→`) move one step at a time, the **Reviewed** checkbox (or `x`) marks the step, and **✓ Reviewed, next** (or `r`) does both. With Settings → *Review view* → *scroll to the first human-review change* on, a step (and a file in Files mode) opens scrolled to its first change in human review. Click a numbered dot to jump; the step opens at its top, even with that setting on. The tab bar and the dots stay pinned under the page header, so a jump never scrolls them out of view. Progress is saved for each result.

### Reviewing

- **Split / Unified** toggle in the toolbar. Split is the default, and the choice is remembered.
- **Expand context** like GitHub: "↑ expand" rows above each hunk and "↓ expand below" at the end of a file load 20 lines at a time from the PR's head commit, with old and new line numbers. **↕ expand all** in a file's header opens every gap at once and shows the whole file; click it again to collapse.
- **Review comments**: hover a line and click **+**. Comments are saved as pending drafts in `.cache/drafts/`, so a reload or restart doesn't lose them. **Review** in the header submits every draft as one GitHub review (Comment, Approve or Request changes) with `gh api repos/{owner}/{repo}/pulls/{n}/reviews`, pinned to the triaged head commit, then clears the drafts. The **+** only appears on lines GitHub accepts: changed lines, and context within 3 lines of a change. Expanded lines can't be commented on. `make ui SERVE_FLAGS=-review-dry-run` shows the payload instead of posting it.

## Fixing issues

In the UI, each review issue has a **Fix issue** button, and the review toolbar has **Fix all issues**. They work on open PRs and local repositories; a merged or closed PR (as of its triage) has them disabled. A fix started from a button waits 5 seconds first, with a toast at the bottom of the window: **Undo** (or Esc) drops it, **Start now** skips the wait. Fixes the chat agent starts don't wait. While a fix runs, the result stays open with a banner showing the fix stage, and **View log** opens the job's activity log in a dialog (clicking the fix in the sidebar's Running list does the same). **Stop**, in the banner, the Issues tab's list of running fixes, or the ✕ on the fix in the Running list, cancels it: the fixer CLI is killed and the fix undoes what it changed, as a failed fix does. A fix can be stopped until it starts committing its changes. The ✕ on a failed job takes it off the list. The fixed result opens when the job finishes. By default, fixes are applied to a persistent local worktree under the app cache, on a branch created at the exact PR head commit. Settings can instead apply fixes directly in the cached local clone. That option checks out the PR head branch there and stops if the clone already has local changes. The PR's head branch name is used when available; a local `pr-manager/pr-N-...` branch is used if that name is already taken. Each round applies a patch and then checks it: the check reviews the issue's unit and units touched by the patch, and asks whether each targeted comment was addressed. The check skips classification, static analysis and the code map. Settings can keep fixing issues these checks find; recursion is on by default and stops after three rounds unless you change the limit. A round works on the targeted issues a check still finds in code the last patch changed (a partial fix gets another try; an issue whose code the fixer left alone is not asked for again), the targeted comments not yet addressed, and new issues at medium or worse. A new low issue is left on the result, and an issue a check had found fixed that comes back in a later round is not fixed again, since that would undo what brought it back; the fix banner counts all of these. Once the rounds end, the fixed code is triaged once: units the fix changed are classified, everything is linted and scored, and the checks' reviews are kept, so nothing is reviewed twice. If a later round fails, the fix keeps the rounds that worked, re-triages them and warns in the fix banner. The new result shows the branch and checkout path.

## The Issues tab, and dismissing what the review got wrong

The **Issues** tab puts every claim anyone has made about the PR in one list, sorted worst first: the review's own issues, the static-analysis findings from step 4, and the open review comments from GitHub. Each row says where it came from and links to the change unit it is about.

A review issue or a lint finding can be **dismissed**. Nothing is deleted: the claim, its evidence and the reason it was rejected all stay on the record, and it stops counting. The unit's attention drops to what is still standing, a review left with nothing earns its clean-review discount back, and the pin a medium-or-worse issue put on the unit lifts, so the unit falls to wherever its score puts it. A pin from a failed review is not something anyone dismissed, and stays. Restoring puts the unit back exactly where the review left it. Likelihood is not touched: it was measured when the PR was triaged, and the finding was real when it was measured.

Dismissals are kept per repository, not per PR, under `dismissed/<host>__<owner>__<repo>.json` in the app cache, and applied whenever a result is loaded. So a claim rejected once arrives dismissed after the next push, without re-running the triage. Each record keeps the unit, the quoted evidence, the severity, the reason, and a `pattern`: the significant words of the title, sorted. An issue is matched on the code it quotes rather than the model's wording, so a reworded claim on the same line is still the same claim. `pattern` is written but not matched on yet; it is what a reviewer that learns from its own record will read.

A finding the review raised more than once, from several units or once in review and once in a GitHub comment, is one row (see *Duplicates* in [how it works](how-it-works.md)). The row is the most severe of them. The other units it was raised on are listed under it as **Also raised on**, and a comment that raised it shows as **raised by @author**. In the Review tab, a repeated issue is listed on its own unit, dimmed, with a link to the issue that stands for it. Dismissing the row dismisses the repeats with it, each under its own record, so they stay dismissed if they are no longer linked after a later push. Restoring the row restores them too.

A GitHub comment has no **Dismiss**: it belongs to whoever wrote it, and resolving the thread on GitHub is what makes it stop counting.

## The Sequence tab

The **Sequence** tab draws the call flow the PR changes: the request or job its changes sit on, as participants and steps. The model returns the shape — participants, steps, which steps this PR changed and which change unit is responsible — and the drawing is done here, so a reply that names a participant it never declared produces a smaller diagram rather than a broken one. A changed step that names a unit is a button: clicking it opens that change in the Review tab. The **Before / After** switch (After by default) shows the flow as the PR leaves it or as it was before: the model marks each step as added, removed or unchanged, and an altered step comes in both forms, so either side is the same list filtered, with no second call. Before highlights the steps the PR removes or replaces. **Copy as Mermaid** gives the side on screen as text, for a PR description. A diagram saved before the switch existed is drawn again the next time the tab is opened.

A triage starts writing it in the background as soon as the result is saved, so the triage itself does not wait for it; opening a result that has none (an older one, or one whose call failed) starts it then, before the tab is opened. It is saved with the result. The call runs at low reasoning effort at most, whatever the review effort: it redraws what the units already say, and on an 11-unit PR medium effort doubled its time (58s against 27-33s) for no better a diagram. A PR with no single flow (a docs change, a formatting pass, unrelated edits) says so instead of inventing one.

## The Code map tab

The **Code map** tab is a treemap of the PR's repo (or **all repos**): repo → directories → files, sized by lines of code and colored by **impact** (red), **likelihood** (green) or **impact + likelihood**, the default: the two ramps blend like overlapping inks, so red is high impact, green is likely to break, and the darkest cells (brightest in dark mode) are both. A 3×3 legend shows the combinations. The green is lighter and yellower than the red at every step, so red-green colorblind readers can still tell them apart. A directory's likelihood is its 75th-percentile file. The PR's units are dots in the file they touch, at their line: filled = human review, ring = skim, small ring = auxiliary, small = no review. Hovering a dot shows its impact (matched map entry, CodeRank, callers, dependent repos, rollback tags) and its top likelihood factors. Hovering an area shows both scores, its commits, fixes, reverts and authors in the last year, and its worst function's complexity. Click an area to zoom in (breadcrumb to zoom out), or click a dot to open that unit in the Review tab: its walkthrough step (a "no review" unit ticks the box that includes them), or its place in the classic list. A table of all changes sits under the map, sorted by risk (click a header to sort by impact, likelihood, bucket or file). `?tab=map` opens the tab directly. The tree comes from `GET /api/codemap/tree?repo=<name|all>`. Diffs for auxiliary and "none" units start collapsed.

## The chat agent

The chat icon at the bottom right, on every tab, opens a chat about the result on screen. The agent gets everything the app has on the change, written out as text: the PR's title, description and commits, the overview, the sequence diagram, each unit's bucket, scores, review notes, issues (dismissed ones are marked, with the reason), lint findings, GitHub threads, code-map impact and likelihood, and the diff (up to about 160K characters, the units on screen first, then from human review down to none). It also gets the fixes made for the PR, your pending review comments, the code map's entries for the changed files and the directories above them (history, complexity, rank and the files that usually change with them), and the activity logs of the triage and fix jobs: every model call's reasoning, the files it read and its raw answer. When a triage or fix job ends, its log is saved under `results/logs/<key>/` with the result it made, and a fix's log is saved with the result it fixed too. A result keeps its 8 newest logs, so the chat still has them after a restart. Results triaged before this have none. git and gh command output is left out. All of this also goes into a folder the agent can search (`context.md` with every diff in full, `logs/INDEX.md` and one file per thread), and the prompt holds an abridged copy with an index of the log files. The folder is the conversation's, under `<cache>/chats/<hash>/material`, rewritten for every question. If the folder can't be written, the prompt gets the end of each thread instead, the threads about the units on screen first, up to about 60K characters. Each question also sends what you are looking at: the tab, the walkthrough step and its units, or the file open in Files mode; the text you selected (in a diff, with its file and its old and new line numbers), kept until you click in the page again, or **clear selection** in the chat; and the text boxes open on the page, with what they say: a review comment you are writing (with its line), the reason of a dismissal, the review summary. So "is this issue real?" means the issue on screen, and "reword my comment" means the one you are typing. The chat's *Looking at* line shows all of it. Asked to, the agent writes into one of those boxes (`fill_field`), replacing its text, or opens a comment box on a line; nothing is saved until you save it. The agent can also read the code: the fix checkout for a fixed result, the working tree for a local review, or else a worktree at the PR head with the PR's agent files removed, the conversation's own (`<cache>/chats/<hash>/code`), kept between questions and removed after a week unused. It can also read every repository the code map indexes (the workspace), the ones that depend on the changed code by name, your own checkout of the PR's repository with its installed dependencies (`node_modules`, a virtualenv), your code directory (`-code-root`), and the Go module and Cargo caches. A reply that names a unit links to it; clicking the link opens that unit in the Review tab.

On codex and claude-code the agent reaches past its sandbox without being able to write. It searches and fetches the web with the CLI's own tools (codex fetches with the app's), and reads GitHub with `gh`, logged in as you: PRs and their comments, checks and CI logs, issues, releases, search, and `gh api` GETs and GraphQL queries, nothing that writes. gh runs in `pr-manager mcp`, a small MCP server the CLI starts outside its sandbox, which refuses any other command. The API providers get the same web fetch and the same read-only gh as tools. Fetch refuses addresses on this machine and the private network. Settings → *Chat agent actions* → *let the chat agent use the web and read GitHub* turns both off. Code from the PR is untrusted, and with the web on, an agent misled by it could send what it read to a site it fetches; turn the web off for PRs you don't trust.

On codex and claude-code each answer carries on the CLI's own session: the agent keeps the files it read and the commands it ran, and is sent only the turns since its last answer, with the material again only when it changed (codex) or as the system prompt (Claude Code). A retry, a new conversation or another model starts a new session with the whole conversation, and so does a session that can't be resumed. When a conversation outgrows the 24 turns a prompt carries, the turns left out are recalled in a short digest of your questions and what the actions did.

While the agent works, the chat shows what it is doing, one line for the step it is on under *Working for 12s*: what it thinks, the files it reads, its searches, commands, gh and web calls, failed ones marked. Click it for every step. The answer keeps them, folded into *Worked for 40s · read 6 files, ran 3 commands* (and *same session* when it carried on its session). Each answer shows the tokens it used, and the chat's header the conversation's so far; cached reads count as input, so a long resumed session adds up fast.

In a Go module the agent on codex and claude-code can also build and test, in its sandbox: `go build`, `go vet`, `go test`. Its build output goes to a directory of the conversation's under the temp directory, the only place it may write; modules come from the module cache, which the app fills with `go mod download` first (nothing of the PR's runs for that), and the sandbox still has no network. Claude Code builds wherever the code is; codex only in the conversation's own worktree, in its workspace-write sandbox, never in your checkout or a fix checkout. A test is the PR author's code, run in that sandbox. Windows has no sandbox for Claude Code, so there it doesn't build.

Asked to look at the page, the agent takes a **snapshot**: a picture of the window as you see it, without the chat panel, which stays where it is. The page is copied without the chat and drawn onto a canvas with its own styles, at the window's size and scroll; nothing is hidden on screen. The picture is kept with the conversation (its 20 newest, under `<cache>/chats/<hash>/snapshots`) and comes with the agent's next turn: attached for codex, a file to read for Claude Code. The page's text comes with it, which is all the API providers get. Where the browser won't draw the page as a picture (Safari, so possibly the macOS app), the text is all there is.

The chat starts every page load collapsed to a small icon. **A** (when you aren't typing in a field) or **Ctrl+/** / **⌘/** (from anywhere) opens it with the cursor in the prompt (Settings → *Chat hotkeys* → *Open* replaces both with a combo of your own, and the icon's hover text names it), and **Esc** or the **–** button collapses it back to the icon. *Collapse* in the same place adds a combo that collapses it from anywhere, not only from inside the chat. Set both to the same combo and it toggles the chat. Drag the icon, or the floating panel by its header, anywhere in the window to get it off the text you're reading. The two share one position, and double-clicking the header puts it back in the corner. Opened, it floats over the page, or **docks** as a column on the right that the page makes room for. Drag its edge (docked) or top-left corner (floating) to resize it. **Pop out** moves it to a window of its own that you can put on another screen. It follows the PR and the view in the main window, and **Put back** returns it there. The desktop app has a single window, so it can only float or dock. Conversations are kept per change, so they carry on across re-triages and fixes, on disk under `<cache>/chats/` (a month after their last use they go), and **+** starts a new one, which also drops the agent's session and worktree. One kept in the browser before moves there when it is first opened. **Enter** sends a question and **Shift+Enter** adds a new line. The model is Settings → Models → *Chat agent*, or `-chat`/`-chat-model`. It follows the reviewer (the analyze model) by default, with the same defaults, at the review effort.

The agent also has a way to dig: on codex and claude-code a read-only shell (`rg`, `git log`, `git show`, `git blame`, `git diff`, `git grep`, `ls`, `cat` and pipes), and on the API providers (claude-api, openai-api, Bedrock, Vertex AI, Foundry, Azure OpenAI, Ollama) tools the app runs for it: `read_file`, `list_dir`, `glob`, `grep` (`rg` when it is installed) and `git` for the commands that read. It is told where the app keeps everything, and may read all of it:

- the code as reviewed;
- the repository's clone with its history, or your checkout for a local review;
- the fix checkout;
- the saved results of every run of the change;
- the saved job logs, where each model call keeps its reasoning and the files it read;
- the pending comments and the dismissals;
- the code map.

Nothing it runs can write or reach the network. Claude Code runs it in its OS sandbox (Seatbelt on macOS, bubblewrap on Linux), with writes denied to everything it reads and to the app's cache, no network, the usual credential folders (`~/.ssh`, `~/.aws`, `~/.config/gh`…) unreadable, and no way to run a command outside the sandbox. Where that sandbox can't start, Windows included, only a list of read-only commands runs (git's reading subcommands, `rg`, `ls`, `cat`, `head` and the like). That list matches commands by how they start, so it is a weaker guard than the sandbox. Codex uses its own read-only sandbox. The agent checks which tools are installed and uses what it finds. Before the first question about a PR, the app fetches the history of the files the PR changes into its blobless clone, so blame and old versions work without the network. On the API providers the model asks for a tool, the app runs it and sends back the output (up to 60K characters a call), until the model answers: at most 40 rounds and 600K characters of output per answer, each round billed as a call. Their tools resolve every path, symlinks included, and refuse one outside those places. `git` runs only its reading commands (`log`, `show`, `blame`, `diff`, `grep`, `ls-files` and the like), without a shell, and refuses the options that write a file, run a program or read outside them (`--output`, `--no-index`, `-O`, `--contents`…). A local Ollama model runs with the context window Ollama is set to (32K tokens is common) and silently drops what doesn't fit, so the app asks Ollama for the loaded model's window and sizes everything to it: the prompt gets half of it (fewer diffs, the newest turns, the rest of the material cut with a pointer to `context.md`), each tool output a fifth, and the oldest tool outputs are dropped once the conversation outgrows it. Ollama's cloud models, and windows of 128K tokens or more, get the full prompt.

### What the agent can do

The agent can also act. Under its answer it lists what it proposes, one card each, with its reason and the text it would post. **Run** (or **Post**) does it and **Skip** declines it. Navigation (open a unit, switch tab) runs at once. Everything else waits for your click, unless Settings → *Chat agent actions* lets edits (pending comments, dismissals, marking units reviewed) or jobs (fixes, re-analysis) run on their own. Anything that posts to GitHub or pushes always waits. The agent is told to act only when you ask, and never because something in the PR asks it to. The actions are:

| Kind | Actions |
|---|---|
| view | `open_unit`, `open_tab` |
| edit | `draft_comment` (a pending comment on a changed line), `delete_draft`, `dismiss` and `restore` an issue or lint finding, `mark_reviewed` |
| job | `fix` (some issues or review threads, or all), `change` (a change you ask for, in the files it names), `reanalyze_units` (review these units again, keeping every other unit's review), `retriage` (the whole change again, incrementally or from scratch), `refresh_comments` (the GitHub review comments), `regenerate` (the overview or the sequence), `reindex_codemap` |
| GitHub | `reply_thread`, `resolve_thread`, `submit_review` (the pending comments), `push_fix` |

A job is followed to its end on the card, with its stage, and the result it makes is opened if you are still on the same change. What each action did goes back to the agent as an event turn with its start and end times, and the agent then continues by itself, at most three answers in a row before you say something. Every turn is timestamped, and the material it gets says when it was gathered, when the result was triaged and when its comments were fetched. A conversation belongs to the change (the PR, or the local checkout), not to one result, so it carries on across re-triages and fixes. GitHub replies and resolutions honor `-review-dry-run`. GitLab is not supported: the app only talks to GitHub, through `gh`.

The agent can't change the code while it answers: its shell and tools only read. When you ask it to change something, it proposes `change`, with your request written out as its instructions and the files it may touch. That runs as a fix job, listed with the other jobs in the left pane: an agent edits a scratch copy of the fix checkout, only those files, and then the change is checked, re-triaged and committed like a fix (on a local review, in a worktree of its own). On codex and claude-code the agent edits the files itself; on the API providers the model returns a patch. Neither can run commands, so it can't build or test what it changed. With *recursive* fixes on, later rounds fix the issues the check finds in the change. The commit is named after the request and shows in the fixes list as a change; `push_fix` pushes it. The instructions come from the chat agent, so read them on the card before you run it.

The same actions are available from the browser console as `window.prm`: `prm.list()`, `prm.result()`, `prm.units()`, and `await prm.run("open_unit", {unit: "..."})`. The server endpoints the actions use beyond the UI's own are `POST /api/results/{key}/reanalyze` (`what`: units, all, threads, overview or sequence) and `POST /api/results/{key}/threads/{reply|resolve}`.

## Settings

The gear button in the header opens **Settings**, in tabs down its side: *Models*, *Review*, *Code map*, *Chat agent*, *Fixes* and *Statistics*. *Statistics* shows the tokens every model call spent, kept under `<cache>/usage` (one line a call): over 7, 30 or 90 days or all time, the totals, a column a day stacked by activity (analysis, chat, fixing, review comments, translation), the split by activity, every repository with its PRs and local branches, each split by activity, and the split by model and by kind of call. Hover a mark for its numbers; the days are also a table. Settings hold the provider and model for each run (separately for the classifier and the summarizer, plus the translator and the chat agent), the review budget slider (More ↔ Less, with this PR's bucket counts at each step) and review tools. The line next to the gear shows the models and budget in use. It only lists providers this machine can run: Codex or Claude Code logged in with a subscription, an API key that is set (`OPENAI_API_KEY`, `ANTHROPIC_API_KEY`), a cloud account (Bedrock, Vertex AI, Foundry, Azure OpenAI, see below), a running Ollama, or OpenJev (classifier only). Hover a provider picker to see why the others are missing. Each provider has its own model list, taken from the provider where it can be read: `codex app-server` `model/list` (as t3code does), the OpenAI and Anthropic `/v1/models` endpoints, and Ollama's `/api/tags`. Claude Code has no list command, so it uses a built-in list. "custom model id…" takes any id. Each role's default is a list, best first, not a single id (`classifyDefaults`, `summaryDefaults`, `translateDefaults` in `main.go`). Where the list is what the endpoint serves (the Anthropic and OpenAI `/v1/models`, including through `ANTHROPIC_BASE_URL`/`OPENAI_BASE_URL` gateways, Ollama, and Azure OpenAI with `AZURE_OPENAI_DEPLOYMENTS`), the default is the first entry the endpoint has, else its newest model of the same family (a gateway with only `claude-sonnet-4-5` gets that for a Sonnet default), else its first model. Codex's list follows the codex profile and leaves out models it runs, and the other providers have built-in lists, so they keep the first entry. Lists are cached for 5 minutes (`GET /api/providers?refresh=1` re-probes), and the picks are remembered in the browser.

## GitHub Enterprise and fetching

Links on any host work, so GitHub Enterprise Server (`https://ghe.example.com/org/repo/pull/7`) and GitHub Enterprise Cloud with data residency (`*.ghe.com`) PRs triage the same way, as long as `gh` is logged in to that host (`gh auth login --hostname ghe.example.com`). `owner/repo#N` uses `GH_HOST` when it is set, else github.com; `host/owner/repo#N` names the host. `prs -repo` takes `host/owner/repo`. Clones, cached results and drafts for Enterprise hosts are kept under the host name, so the same owner/repo on two hosts don't collide; github.com keeps the names it had.

Installed commands store data in the [user cache directory](install.md#data-and-code-maps); the `.cache` paths below describe the Makefile development defaults.

How a PR is fetched: `gh pr view` resolves it, then a blobless clone under `.cache/repos/` fetches `refs/pull/N/head`. The diff runs against the fork point. For merged PRs that's the base branch just before the merge commit, so the diff matches what the PR changed, and source files are parsed at the PR head. `.triage.yaml` and `.gitattributes` are read from the PR head. Results are cached in `.cache/results/`, keyed by PR head SHA, providers, models and prompt version. Pressing **Triage** on a PR that is already cached at its current head asks whether to run it again. Cancel opens the saved result. On the command line, `-force` skips the cache.
